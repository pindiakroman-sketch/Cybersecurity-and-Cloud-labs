## 1. Objective

Investigate how a hidden login page combined with weak credentials can expose a web application to unauthorised access.

The exercise introduced password dictionary attacks and demonstrated how Hydra automates login attempts against a web form. It also illustrated how seemingly minor weaknesses can be chained together to create a more significant security risk.

## 2. Technical Investigation

### 2.1 Attack Surface Discovery

A login page was identified during the previous stage of the exercise.

A hidden or unlinked login page is not necessarily a vulnerability by itself. However, authentication functionality may become a target when combined with weak passwords, insufficient rate limiting, or other authentication weaknesses.

### 2.2 Manual Credential Testing

The exercise used the username `admin` and a predefined list of common passwords:

```text
abc123
123456
password
qwerty
654321
```

The objective was to determine whether any of these credentials could authenticate successfully.

### 2.3 Automated Dictionary Attack with Hydra

Hydra automates authentication attempts using a predefined password list.

The command used in the lab was:

```bash
hydra -l admin -P passlist.txt www.onlineshop.thm http-post-form "/login:username=^USER^&password=^PASS^:F=incorrect" -V
```

**Command breakdown:**

| Argument | Purpose |
|---|---|
| `-l admin` | Specifies the username to test |
| `-P passlist.txt` | Specifies the password wordlist |
| `www.onlineshop.thm` | Specifies the target hostname |
| `http-post-form` | Selects Hydra's HTTP POST form module |
| `/login` | Specifies the login endpoint |
| `username=^USER^` | Inserts the username being tested |
| `password=^PASS^` | Inserts the current password candidate |
| `F=incorrect` | Treats a response containing the configured failure text as a failed login |
| `-V` | Displays detailed output for individual attempts |

The failure indicator must match the target application's actual response. If it is configured incorrectly, Hydra may misidentify successful or unsuccessful attempts.

### 2.4 Credential Validation

After identifying a candidate password, the exercise required logging in through the web interface and examining the resulting page.

A successful authentication demonstrates that the tested credentials are valid for the lab application. The account's actual permissions determine what functionality becomes accessible.

## 4. Remediation & Mitigation

- **Enforce strong passwords:** Block common and easily guessed passwords.
- **Implement rate limiting:** Restrict repeated login attempts and introduce appropriate delays.
- **Use multi-factor authentication (MFA):** Add another verification factor to reduce the impact of compromised passwords.
- **Monitor authentication activity:** Detect repeated failures, unusual login patterns, and potential dictionary attacks.
- **Protect administrative accounts:** Apply least privilege and avoid exposing unnecessary administrative functionality.
- **Use secure authentication controls:** Consider progressive delays, risk-based challenges, and carefully designed account lockout policies to reduce abuse without creating denial-of-service opportunities.

## Key Takeaway

A login endpoint combined with weak credentials can allow unauthorised access. Dictionary attacks demonstrate why password strength, rate limiting, MFA, and authentication monitoring are important defensive controls.

This exercise also introduced the concept of chaining weaknesses: multiple issues can combine to produce a greater impact than any one issue considered in isolation.
