# 🛡️ Decrypting HTTPS Traffic and Network Packet Analysis with Wireshark

This repository contains my documentation, technical notes, and step-by-step solution for the network security challenge focused on traffic analysis, transport-layer encryption, and cryptographic session key management.

The objective of this lab was to evaluate how transport-layer encryption transforms cleartext protocols (HTTP) into secure alternatives (HTTPS) to prevent eavesdropping and Man-in-the-Middle (MitM) attacks.

---

## 🔍 Core Security Architecture: HTTP vs. HTTPS

Understanding the foundational transition from plain text to encrypted transport is crucial for modern network defense:

*   **HTTP (Insecure Transport):** Transmits application-layer payload in plaintext over TCP port 80. Any intermediate router or network tap can effortlessly intercept, reconstruct, and read sensitive data (e.g., credentials, session cookies).
*   **HTTPS (Secure Transport via TLS):** Encapsulates standard HTTP traffic within a cryptographically secure TLS (Transport Layer Security) tunnel, typically over port 443. To any third-party packet sniffer, the payload yields nothing but pseudo-random cryptographic ciphertext.

### 🤝 The End-to-End Secure Connection Lifecycle:
1.  **TCP Three-Way Handshake:** Establishing the stateful transport connection via a 3-packet sequence (`SYN` ➡️ `SYN-ACK` ➡️ `ACK`).
2.  **TLS Cryptographic Negotiation:** In this environment, the negotiation spanned exactly **8 packets**. During this handshake, the client validates the server's X.509 digital certificate to authenticate identity, and both nodes dynamically negotiate the cipher suite and derive ephemeral symmetric encryption keys.
3.  **Encrypted Application Exchange (HTTP/2):** Data is transmitted natively under the `Application Data` abstraction layer.

## 💻 Technical Challenge Walkthrough

**Objective:** Isolate and extract a user's plaintext login credentials from an encrypted network capture file (`randy-chromium.pcapng`).

### 🛠️ Step 1: Session Key Injection & TLS Decryption
Because the browser's environment variable was configured to dump symmetric secrets (`chromium --ssl-key-log-file=~/ssl-key.log`), I leveraged the `Pre-Master-Secret` log file to decrypt the TLS layer locally inside Wireshark.

1.  Opened the packet capture file (`.pcapng`) inside Wireshark.
2.  Right-clicked an arbitrary **TLS** packet to navigate the protocol tree.
3.  Selected **Protocol Preferences** ➡️ **Transport Layer Security** ➡️ **Open Transport Layer Security preferences...**
4.  In the configuration dialog, mapped the **(Pre-Master-Secret log filename)** field directly to the local `ssl-key.log` file.
5.  Saved changes, forcing Wireshark to dynamically compute the session keys and retroactively decrypt the stream.

### 🕵️ Step 2: Protocol Filtering & Payload Inspection
1.  With the underlying stream decrypted, I isolated the optimized HTTP framework by applying the display filter: `http2`.
2.  Inspected **Packet #366**, which contained an outbound HTTP `POST` request directed at the authentication endpoint (`POST /login/...`).
3.  Expanded the dissected **HyperText Transfer Protocol 2** protocol tree in the packet details pane to expose the unencrypted parameters.

## 📚 Network Architecture Security Paradigms (Executive Summary)

This challenge highlights the three foundational approaches to network data protection addressed during the module:

1.  **TLS (Transport Layer Security):** Transparently encapsulates application-layer protocols (e.g., HTTPS, SMTPS, POP3S) without requiring re-engineering of the network or internet layer.
2.  **SSH (Secure Shell) Tunneling:** Ideal for securely port-forwarding legacy or insecure protocol traffic (such as VNC or database queries) over an encrypted point-to-point tunnel.
3.  **VPN (Virtual Private Network):** Broad-scale architecture designed to encapsulate entire network boundaries, commonly utilized to establish secure site-to-site topologies between corporate branches.
